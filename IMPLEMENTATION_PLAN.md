# Sales OS 2.0 — план реализации по milestones

**Статус:** архитектурный план, разработка приложения ещё не начата.  
**Исходные материалы:** `index.html` (Sales OS v1), `sales-knowledge-base.zip` (446 Markdown-файлов), `DESIGN-vercel.md` (обязательная дизайн-система).  
**Цель:** статически публикуемое, быстрое, удобное, адаптивное учебное приложение на русском языке, работающее с существующими Markdown-файлами: 4 уровня → 22 модуля → 336 уроков и 72 упражнения; прогресс, заметки, поиск, источники, светлая/тёмная тема, по возможности офлайн-использование. Холодные звонки не добавлять; практика ориентирована на текстовые продажи сайтов и IT-услуг.

## 1. Архитектурное решение

### Рекомендуемый стек

| Подсистема | Решение | Обоснование |
|---|---|---|
| Framework | **Astro**, статическая генерация (`output: 'static'`) | Контентно-ориентированный сайт: более 400 образовательных страниц без необходимости собственного сервера. |
| Типы | **TypeScript** в строгом режиме | Стабильные ID, маршруты, состояния, отсутствие незаметных несовпадений между данными. |
| Интерактивность | **React islands** + при необходимости `nanostores` | Гидратация только для поиска, прогресса, фильтров, заметок и интерактивных заданий, а не всего учебного текста. |
| Стили | **Tailwind CSS 4** через Vite + CSS custom properties | Прямая реализация токенов `DESIGN-vercel.md`, единая тема и адаптивность. Не использовать устаревшую конфигурацию Tailwind v3 как основу Tailwind v4. |
| Контент | **Astro Content Collections** (`glob` loader) + **Zod** | Проверка Markdown/YAML во время сборки, типизация, статические URL. |
| Разметка | Стандартный Markdown; MDX только для новых материалов, где обоснована необходимость | Не преобразовывать без нужды исходные 446 `.md` в `.mdx`. |
| Поиск | **Pagefind** по построенным статическим страницам | Локальный статический поисковый индекс, без внешней поисковой службы. |
| Данные пользователя | `localStorage` для настроек/небольшого прогресса; **IndexedDB** для объёмных заметок и ответов | Local-first, без логина и бэкенда в MVP. Слой репозитория данных, схема и миграции. |
| Иконки | Lucide (16px, stroke 1.5 там, где соответствует дизайн-файлу) | Консистентность. |
| Тестирование | **Vitest** (логика) + **Playwright** (E2E и визуальные сценарии), `astro check`, ESLint, Prettier | Проверяемое прохождение milestones. |
| Хостинг | Статический деплой (Vercel / Netlify / Cloudflare Pages / иной) | Бесплатные тарифы возможны при подходящих условиях; не нужен постоянно работающий сервер. |

**Почему не Next.js:** для локально хранимой учебной программы не требуется SSR, API-сервер и управляемая база данных. Next.js уместен позже, если появятся аккаунты, совместная работа, серверная проверка или платная подписка. **Почему не Vite React SPA:** SPA удобна для единого интерактивного состояния, но Astro лучше структурирует и отдаёт сотни Markdown-страниц как готовый HTML. Использование интерактивных islands и общей data-store требует аккуратной архитектуры; не следует без необходимости делать весь сайт одним React-островом.

**Важное архитектурное решение:** итоговый production build — **статический многостраничный сайт**, а не один монолитный `index.html`. Приоритет — производительность, маршрутизация, поиск, обновляемость, SEO/доступность. Позднее можно исследовать отдельный переносимый формат, но он не является блокером MVP. Для офлайн-доступа реализовать PWA/service worker на выделенном этапе. Новая версия **не должна зависеть от интернет-запросов для получения основного содержимого после корректной установки офлайн-набора**.

### Источники истины и ограничения

1. Источником истины для образовательного контента служит распакованная **копия без ручной потери данных** `sales-knowledge-base/` (336 уроков, 72 практики, 22 обзора, 6 каталогов источников, 10 системных документов).
2. Источником истины для старых отметок и порядка изучения служит `index.html` v1. ID новой версии — исходные `01-001`, `01-P01`, `01-MODULE` и т. п., а не позиции массива.
3. Источником истины для UI служит **`DESIGN-vercel.md`**, включая light/dark, токены, состояние фокуса, отступы, адаптивность, motion и типографику.
4. В Markdown на данный момент стоит `status: editorial_draft`: **автоматически объявлять эти материалы «научно проверенными» недопустимо**. В интерфейсе отражать редакционный статус; наличие ссылки на книгу или видео не означает фактологическую проверку каждого утверждения.
5. Каталоги источников (`BOOKS.md`, `VIDEOS.md`, ... ) имеют человеческий Markdown-формат. Для карточек источников нужен **отдельный проверяемый парсер/нормализатор** или нормализованный индекс, собираемый из этих файлов, без выдумывания метаданных.
6. Юридические материалы, правила платформ и рекомендации по переписке отображать с предупреждением об актуальности и юрисдикции. Не генерировать отправку массовых рассылок или функции холодных звонков.

## 2. Информационная архитектура и маршруты

| Маршрут | Назначение |
|---|---|
| `/` | Главная: продолжить обучение, прогресс и ближайшая практика |
| `/roadmap/` | Компактная карта **четырёх уровней** и всех 22 модулей, без полной простыни тем |
| `/level/[id]/` | Модули одного уровня |
| `/module/[id]/` | Один выбранный модуль: тематические группы, уроки и задания **только этого модуля** |
| `/lesson/[id]/` | **Один конкретный** теоретический Markdown с оглавлением, связанными заданиями и источниками |
| `/practice/[id]/` | **Одно конкретное** упражнение: постановка задачи, шаблон ответа, критерии, заметки |
| `/sources/` | Каталог источников, поиск и фильтры |
| `/source/[id]/` | Карточка источника, ссылки и связанные темы, если запись проверена |
| `/bookmarks/` | Сохранённые уроки и задания |
| `/final-project/` | Сквозной проект по продаже сайта |
| `/settings/` | Тема, доступность, резервная копия/импорт, офлайн-кэш |

**Навигация:** sidebar шириной **240px** на desktop, **64px** в tablet collapsed mode, на mobile — закрываемое меню/доступный sheet. В sidebar: «Обзор», «Roadmap», группировка по четырём уровням (вложенные **22 модуля**, но **не 336 уроков**), «Практика», «Источники», «Закладки». Клик по модулю **заменяет содержимое центральной области**. Внутри модульной страницы — компактные группы тем. На странице урока — breadcrumbs, соседние темы и локальное оглавление. Прямые ссылки на уроки, `Back/Forward`, обновление и открытие в новой вкладке работают.

## 3. Дизайн-контракт по DESIGN-vercel.md

| Элемент | Light | Dark |
|---|---|---|
| Главный фон | `#ffffff` | `#000000` |
| Вторичный фон | `#fafafa` | `#0a0a0a` |
| Третичный фон | `#f5f5f5` | `#111111` |
| Основной текст | `#000000` | `#fafafa` |
| Вторичный текст | `#666666` | `#888888` |
| Ссылки мелкого кегля | `#0761d1` | `#3291ff` |
| Бордюр по умолчанию | `#e8e8e8` | `#2e2e2e` |
| Слабый бордюр | `#ededed` | `#1a1a1a` |
| Primary button | чёрная с белым текстом | белая с чёрным текстом |
| Активный sidebar item | чёрный/белый | белый/чёрный |

- **Geist** для всех UI/учебных текстов, **Geist Mono** для кода; подключение через официально разрешённый пакет/источник. Использовать системные fallback только при технической необходимости.
- Радиусы: `6px` для buttons/inputs, `8px` для карточек, максимум `12px` для больших панелей; pill только для badges/avatars.
- Основной рельеф через границы 1px, тяжёлые тени и декоративные градиенты **не добавлять**. Радужный градиент допустим лишь в редких декоративных hero-ситуациях, но для учебного dashboard лучше вовсе не использовать.
- Typographic scale из дизайн-файла; длинный контент читается в колонке примерно **720–820px**, line-height ~1.6; исключить слишком длинную строку.
- Navbar — светлая/тёмная полупрозрачная поверхность с blur 8px, sticky и чёткой границей; footer при наличии всегда `#000000` (в приложении допустим минимальный footer).
- Motion 100–200ms, easing `cubic-bezier(0.25,0.46,0.45,0.94)`, никаких bounce/spring. `prefers-reduced-motion` обязательно.
- Accessibility: `:focus-visible` ring 2px; WCAG AA: обычный текст не использовать `#888888` на белом; для мелких ссылок light — `#0761d1`; touch targets 44×44px, клавиатура, ARIA, достаточный контраст.
- Theme control: **Светлая / Тёмная / Системная**. Поначалу уважать `prefers-color-scheme`; явный выбор запоминать, менять без мерцания темы при загрузке. Проверить переход системной темы и обновление вкладки.
- Из документа брать **токены и принципы**, а не подменять фирменный знак Sales OS логотипом Vercel.

## 4. Правила прохождения milestones (обязательный quality gate)

Каждый milestone — **отдельная законченная вертикальная поставка**. Не начинать следующий, пока текущий не принят. Каждая поставка должна содержать:

1. Короткий отчёт «что сделано / что не делали» с перечислением изменённых модулей и файлов.
2. Фактический результат: запускаемая версия приложения или готовые используемые ресурсы/проверки (для исследовательского этапа).
3. Выполненные **DoD** (Definition of Done) и воспроизводимые команды проверок.
4. Автоматические тесты, соответствующие milestone; проверку базовой регрессии предыдущих milestones.
5. Ручной визуальный осмотр **light и dark** как минимум desktop 1440px и mobile 390px (для инфраструктурных этапов — соответствующий smoke test).
6. Исправление всех ошибок класса «блокер», падений сборки, ошибок навигации, утери данных, проблем доступности критических действий.
7. Коммит/точку восстановления и обновление журнала `docs/MILESTONE_LOG.md`.

Если DoD не достигнут: **остаться в том же milestone, исправить и повторить проверки**, а не перенести проблемы на потом. Предварительное самоподтверждение не заменяет фактический запуск тестов. Отложенные некритичные улучшения заносить в backlog с понятным объяснением, не скрывать их в отчёте.

## M0 — Инвентаризация и фиксация эталона (baseline)

**Цель:** понять, что существует, и не потерять данные во время миграции.

**Задачи:**
1. Зафиксировать исходный `index.html`, его экраны, структуру `modules`, отображение, поиск, фильтры и localStorage ключ `sales-os-roadmap-v1`.
2. Распаковать `sales-knowledge-base.zip` в проект без правки исходных `.md` и пересчитать файлы: **22 модуля, 336 уроков, 72 практики, 6 каталогов, 10 системных**.
3. Проверить YAML, ID, пересечения названий, межфайловые ссылки, `sources`, `related_practice`, группировки, статусы `editorial_draft`. Создать machine-readable manifest ID → `kind`, `module`, `group`, `level`, путь и порядок.
4. Сверить исходный порядок уроков и практики с `ROADMAP_MAP.md`. Составить отображение старых позиционных ключей `t-mi-ti-ii`, `p-mi-li` в новые ID.
5. Провести аудит источников отдельно от валидности ссылок: сохранить статус непроверенных утверждений/транскриптов.
6. Зафиксировать структуру репозитория и non-goals: без личного кабинета, платёжной системы, холодных звонков, отправки массовых сообщений, искусственного AI-оценщика в MVP.

**Артефакты:** `docs/BASELINE.md`, `src/generated/content-manifest.json` (или генерируемый аналог), `scripts/validate-content.*`, `docs/MIGRATION_MAP.md`, snapshot исходников.

**DoD и проверка:** manifest включает **ровно 22/336/72** (на основе реально найденных файлов); **нулевые дубликаты ID и сломанные локальные ссылки**; отчёт перечисляет все несоответствия, если обнаружатся; ключи для миграции покрывают все исходные отметки; начальные файлы сохранены неизменёнными.

## M1 — Каркас Astro и воспроизводимая сборка

**Цель:** получить работающий современный проект с минимальной страницей.

**Задачи:**
1. Создать Astro + TS strict; установить React integration, Tailwind 4, пакеты QA и lockfile; зафиксировать совместимые стабильные версии.
2. Настроить единый `AppLayout` и маршруты заглушек, локальную разработку и статическую генерацию. База URL должна корректно работать при размещении на корне домена или подпути (если заявляется такой способ хостинга).
3. Обеспечить `lang="ru"`, семантическую HTML-разметку, корректную страницу 404.
4. Создать базовые скрипты: `dev`, `build`, `preview`, `check`, `lint`, `test`, `test:e2e` и инструкции для Windows PowerShell.
5. Подключить CI с проверкой статической сборки.

**DoD:** чистая установка зависимостей, `npm run check`, `npm run build` и `npm run preview` работают; базовые маршруты доступны; нет runtime console errors; нет сервера/API, необходимых для просмотра опубликованной версии.

## M2 — Полная дизайн-система, две темы и базовые компоненты

**Цель:** создать готовый UI-фундамент и добиться визуального соответствия `DESIGN-vercel.md`.

**Задачи:**
1. Перенести все применимые токены (light/dark, 12-step grays, spacing, typography, radii, transitions, z-index) в `src/styles/tokens.css` и интеграцию Tailwind 4.
2. Подключить Geist/Geist Mono корректным способом; сделать коллекцию компонентов: Button, IconButton, Card, Badge, Tabs, Breadcrumbs, Input, Select, SearchInput, Dialog, Dropdown, Tooltip, Toast, ProgressBar, Skeleton, MarkdownTypography.
3. Implement theme switch: Light/Dark/System, persisted preference, anti-flash inline boot script, `prefers-color-scheme`, update `color-scheme` для полей.
4. Создать визуальный каталог/страницу проверки компонентов и всех состояний: default/hover/focus/disabled/error/loading.
5. Отработать адаптивность с самого начала: 390, 768, 1024, 1440px; тесты клавиатуры и reduce-motion.

**DoD:** на компонентном стенде **все компоненты видны и работоспособны в обеих темах**; выбранная тема сохраняется после перезагрузки; системный режим реагирует на системную тему; нет неправильных радиусов, теней или недостаточного контраста для основного текста; Playwright-проверки light/dark + mobile/desktop проходят. До M3 не переходить, пока интерфейсные токены не стабилизированы.

## M3 — Загрузка и проверка Markdown как настоящих страниц

**Цель:** все существующие материалы становятся источником данных приложения.

**Задачи:**
1. Настроить Content Collections для `module`, `theory`, `practice` с `glob` loaders и строгими Zod-схемами; учесть существующие поля `id`, `module`, `kind`, `level`, `group`, `status`, `updated`, `sources`, `related_practice`.
2. Проверять, что 336 + 72 + 22 статей индексируются. Сохранять исходные Markdown и их контент, включая таблицы, списки, блоки кода и относительные ссылки.
3. Создать единый resolver исходных относительных `.md` ссылок: навигация ведёт на **маршруты приложения**, не на 404/скачивание `.md`.
4. Построить индекс источников (Bxx, Cxx, Sxx и т. д.) из существующих шести каталогов; определить допустимые и неизвестные связи.
5. Отдельно обрабатывать внешние ссылки: валидация протоколов, `rel="noopener noreferrer"`, запрет небезопасного HTML/скриптов из контента; никаких автоматических сторонних видео-iframe без явного действия.
6. Проверить `editorial_draft` и предусмотреть видимую редакционную пометку, а не обещание полной верификации.

**DoD:** все 430 Markdown-единиц содержания (22+336+72) доступны в реестре без потери ID; любой файл, нарушающий схему, ломает сборку с понятным сообщением; **0 неразрешённых внутренних ссылок и source IDs** либо полностью задокументированный список требующих коррекции; XSS-тесты проходят; минимум пять разных типов длинных/сложных Markdown корректно отрисованы в light/dark.

## M5 — Полноценный читательский экран урока

**Цель:** создать удобный интерфейс освоения отдельных тем.

**Задачи:**
1. `/lesson/[id]/`: метаданные, чёткий заголовок, цель, весь Markdown, локальное оглавление H2/H3 со ссылками на anchor, источники, связанные практики.
2. Читательская колонка 720–820px, комфортные размеры/межстрочные интервалы, контрастные code/table/blockquote/list, горизонтальная прокрутка широких таблиц на мобильном.
3. Навигация «предыдущий / следующий урок» внутри правильной последовательности, «к модулю», ссылки по темам.
4. Пометки `editorial_draft`, осторожные дисклеймеры там, где речь о праве, регулировании, специфичных каналах продаж.
5. Сохранение scroll на открытом уроке опционально, но не определять «освоен» по факту доскролла.

**DoD:** все 336 уроков генерируются по прямым URL; контент не обрезан, исходные Markdown-таблицы/вставки отображаются; ссылки и оглавления не ломаются; prev/next корректен на границах модулей; нет горизонтального overflow страницы на mobile; визуальные скриншоты на двух темах проходят.

## M6 — Практический режим и итоговый проект

**Цель:** практика становится самостоятельной частью системы, а не чекбоксом.

**Задачи:**
1. `/practice/[id]/`: цель, связанная теория, условия, необходимые материалы, шаги, критерии результата, образец/рубрика, пометка «учебный кейс» или «реальный проект».
2. Поле ответа/рабочих заметок и собственная самооценка по критериям, автосохранение; необязательно загрузка больших файлов, но можно добавлять локальные ссылки и структурированный текст. Без отправки чужих данных на внешний сервер.
3. Связь урок ↔ упражнение; список практик внутри страницы модуля; автономная страница всех 72 практических задач с фильтрами.
4. `/final-project/`: сквозной процесс поиска заказчика → анализ → первое текстовое сообщение → discovery → КП → согласование условий → предоплата → реализация → отзыв.
5. Если пользователь ещё не получил реального клиента, учебная симуляция и критерии качества доступны без фиктивных подтверждений сделки.

**DoD:** все 72 практики доступны; ответ и критерии оценки сохраняются после обновления и закрытия вкладки; упражнения правильно связаны с темами; отсутствие ответа не отображается как «проверено»; итоговый проект связан с релевантными уроками; данные не передаются в сеть без согласия.

## M7 — Система освоения, миграция старого прогресса и резервные копии

**Цель:** безопасное локальное состояние по стабильным ID.

**Задачи:**
1. Согласовать конечную модель уроков: `not_started`, `in_progress`, `theory_completed`, `mastered` (вне зависимости от того, как называется отображаемая локализованная метка). Для практики: `not_started`, `in_progress`, `self_reviewed`/`completed`; не выдавать самооценку за внешнюю аттестацию.
2. Вывести формулу прогресса по теории и практике отдельно, учитывать обязательные/продвинутые и избежать двойного подсчёта.
3. Разработать хранилище с версионируемым JSON-представлением, миграциями, безопасной обработкой ошибок и экспортом/импортом; данные заметок — IndexedDB, выбор темы и компактный прогресс — localStorage либо единый IndexedDB по контракту.
4. **Мигрировать v1**: читать формат `sales-os-roadmap-v1`, ключи `t-mi-ti-ii`, `p-mi-li`; по фиксированной карте переносить отметки и заметки; старый true-check не считать автоматически доказательством освоения навыка (перенос как «теория изучена»/«практика выполнена по старой самоотметке» с маркировкой наследия).
5. **Особенность безопасности браузеров:** новый сайт **не может сам считать localStorage** предыдущего сайта, если старый запускался с `file://`, а новый открыт с `https://...` — разные origin. Для таких случаев необходим экспорт JSON в старом приложении → импорт в новом.
6. Предупреждения о конфликте импортируемой и существующей истории, backup перед импортом, обработка неправильных файлов.

**DoD:** тестовый fixture старого экспорта переносит все 336/72 ключа и заметки без потери и ложного `mastered`; экспорт → очистка → импорт возвращает состояние; обновление страницы, переключение тем и вкладок не теряют данные; испорченный JSON и дважды импортированный файл не ломают приложение.

3. Фильтры обязательных/продвинутых, статусов, текущего уровня; состояния «ещё не начато», пустой прогресс, все пройдено.

**DoD:** никакой экран не превращается в единую простыню 22 модулей с раскрытыми материалами; счётчики в dashboard и module совпадают с первичными данными; клики во все 22 карточки открывают корректные страницы; 2 темы и 3 разрешения протестированы.

## M9 — Полнотекстовый поиск, библиотека источников, закладки и заметки

Обновление приложения не уничтожает заметки. Установленный лимит на тестовый bundle/shell соблюдён, без необоснованного требования «всё одним HTML».

## 6. Организация работы, релизов и отката

- **Не начинать milestone N+1, пока milestone N не соответствует DoD.** При обнаружении дефекта откатиться к последнему стабильному коммиту или исправить текущую поставку.
- После каждого этапа обновлять `docs/MILESTONE_LOG.md` в формате: цель, изменённые файлы, команды тестирования, результат тестов, скриншоты, известные ограничения, статус `PASS/FAIL`.

- Содержание Markdown и порядок курса — совместимые данные, не производить массовое переписывание статей ради вёрстки. Все нормализации должны быть обратимы либо выполняться на этапе сборки.
- Режимы «регистрация», «синхронизация нескольких устройств через облако», «AI-проверка ответов», «CRM настоящих лидов», «рассылки» — **за рамками первой готовой версии**. Архитектуру не блокировать на случай будущего добавления, но сейчас не имитировать несуществующие функции.
