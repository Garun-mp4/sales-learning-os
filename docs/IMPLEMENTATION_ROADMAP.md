# План внедрения улучшений Sales OS

**Основание:** полный аудит от 8 октября 2026 года, `docs/AUDIT_2026-10-08.md`, и действующий визуальный контракт `DESIGN-vercel.md`.
**Назначение:** актуальный план исправлений и развития уже существующего проекта. Это план будущей работы, а не отчёт о выполненных изменениях.
**Текущий статус на 2026-10-09:** M0 — PASS; M1 — PASS после CI Windows/Linux и проверки Vercel Preview; M2–M8 — не начаты.

## Целевой результат

Sales OS остаётся статическим, privacy-first учебным приложением: уроки читаются без учётной записи и backend, пользовательские данные по-прежнему хранятся локально, а существующие форматы экспорта `sales-os-roadmap-v1`/`sales-os-v2` и исходный Markdown сохраняют совместимость. После прохождения всех milestones приложение должно надёжно сохранять работу, полноценно работать на телефоне и компьютере, иметь доступную навигацию и честные состояния ошибок, индексировать весь согласованный учебный корпус, предсказуемо работать офлайн и последовательно соблюдать адаптированную для Sales OS дизайн-систему Vercel.

План не превращает учебный продукт в копию сайта Vercel: в нём остаются задачи Sales OS и русскоязычный контент. Из дизайн-системы берутся роли, контраст, типографика, сетка, границы, состояния компонентов и сдержанное движение. Доступность имеет приоритет над буквальным копированием спорных примеров из дизайн-файла: значимый обычный текст должен проходить WCAG AA, даже если исходный пример допускает менее контрастный серый.

## Правила выполнения

1. Работать по одному milestone за раз. Следующий этап не начинается, пока предыдущий не прошёл собственные проверки и регрессию. Редакторская проверка учебного корпуса в M5 — отдельный gate: её незакрытый статус не блокирует независимую инженерную работу, но блокирует заявление, что курс фактологически проверен или полностью готов.
2. До изменения реализации записать текущую ветку, commit и состояние рабочей копии. Не включать в коммиты предоставленные пользователем исходники логотипа, если задача этапа — только план или код.
3. Считать Astro основной исходной реализацией и путём публикации на Vercel. Сохранить Python-сборку как проверяемую автономную резервную версию, но развести каталоги вывода так, чтобы сборки не очищали и не перезаписывали общий `dist/` одновременно. Для Vercel собирать из исходников по lockfile; не публиковать случайно устаревший закоммиченный результат.
4. Исходные учебные Markdown-файлы и устойчивые ID не переписывать массово ради вёрстки. Структурные изменения делать через сборку, проверяемые миграции или небольшие тематические редакторские итерации.
5. Не выдавать локальное сохранение за облачную синхронизацию, самооценку — за сертификацию, а техническую проверку Markdown — за фактологическую рецензию курса.
6. Вести `docs/MILESTONE_LOG.md`: цель и границы этапа, изменённые области, команды и фактические результаты проверок, визуальные доказательства для UI-работ, ограничения и статус PASS/FAIL. При FAIL исправлять этап, не переносить скрытые долги дальше.
7. Для каждой проверки сохранять различие между дефектом реализации, уже существовавшей проблемой окружения и непроверенным сценарием. Тест считается пройденным только после фактического успешного запуска.

### Общий критерий готовности milestone

- Изменение соответствует архитектуре и этому плану; существующие пользовательские данные и обратная совместимость сохранены.
- Пройдены целевые тесты этапа и регрессионные сценарии затронутых ранее исправлений.
- Для интерфейсных изменений проверен реальный браузерный рендер в светлой и тёмной темах и на целевых ширинах; скриншоты добавлены в материалы проверки.
- Нет новых ошибок сборки, браузерных исключений, потерянного фокуса, ложных сообщений об успехе или неисправимых внутренних ссылок в затронутом потоке.
- Документация и журнал отражают фактическое состояние, а не предполагаемый результат.

## M0 — Зафиксировать рабочий baseline и границы поставки

**Цель:** превратить выводы аудита в проверяемую стартовую точку реализации и исключить конкурирующие представления о том, какая сборка считается продуктом.

**Работы**

- Использовать уже выполненный аудит и его доказательства как исходный baseline; не повторять полный обход 475 маршрутов без причины.
- В начале работы над кодом зафиксировать актуальные Git status/commit и запустить доступные проверки без исправления дефектов. Сопоставить фактический результат с сохранёнными данными аудита: Astro check, Windows-пути, service worker, статический тест, тесты хранилища и доступность настоящего Playwright-браузера.
- Подтвердить целевой путь поставки: Astro производит Vercel build, Python остаётся отдельно запускаемым fallback. Разделить каталоги вывода/временные артефакты; определить, какие генерируемые файлы коммитятся и какие всегда пересобираются.
- Зафиксировать поддерживаемые версии Node и Python, ОС и браузерные движки для CI. Сохранить статическую модель и локальную приватность.

**Выход:** короткая baseline-запись в `docs/MILESTONE_LOG.md`, согласованное описание источников истины в `docs/ARCHITECTURE.md` и список известных до исправлений ошибок. Изменение исходников приложения на этом этапе не требуется.

**Приёмка:** участники одинаково понимают команду production-сборки, назначение fallback-сборки и перечень воспроизводимых исходных ошибок. Ни один исходный документ или пользовательский файл не потерян.

## M1 — Воспроизводимая сборка, проверки и доставка

**Аудит:** F09, F35, F36, F37, часть F38; финальные release-проверки также в M8.

**Работы**

- Сделать чистую установку воспроизводимой: npm ci использует существующий package-lock, Python requirements объявляет прямые импорты, включая Jinja, а браузерные бинарники Playwright устанавливаются и кэшируются единым документированным способом.
- Нормализовать пути через относительные сегменты и URL-разделители; тестировать Windows и POSIX без предположений о слешах. Согласовать проверяемое число страниц с manifest сборки и добавить явную страницу приложения для 404.
- Развести Astro и Python build outputs и убрать побочные production-сборки из lint/check-команд. Разработка, проверка и сборка не должны незаметно удалять общий `dist/`.
- Устранить подтверждённую критическую уязвимость Astro до безопасной поддерживаемой версии и зафиксировать lockfile; запускать production-зависимости через `npm audit`.
- Настроить Vercel на установку по lockfile и сборку исходников Astro; отдельно документировать запуск и тест резервной Python-версии.
- Обновить устаревшие утверждения в README, ARCHITECTURE, QA_REPORT и handoff-документах о том, что Astro build не запускался. Отметить, какие проверки теперь действительно запускались и где.
- Ввести настоящие lint/format gates для JavaScript и CSS, чтобы они проверяли качество синтаксиса и форматирование, а не только наличие или хэш файлов. Разбивать монолитный код постепенно и по обязанностям, без переписывания приложения целиком.

**Проверки и выход**

- Чистый checkout на Windows и Linux проходит установку из lockfiles, Astro check, lint, Python/Node-тесты и обе сборки.
- Astro и fallback выдают ожидаемые страницы и независимые артефакты; параллельный dev/build не повреждает выходные каталоги.
- Vercel preview строится из текущих исходников; сломанная внутренняя ссылка или пропущенный маршрут останавливают gate.
- CI действительно устанавливает поддерживаемый браузер и запускает E2E через HTTP URL, а не только в искусственно встроенном HTML.

## M2 — Надёжное local-first хранилище и честное сохранение

**Аудит:** F01, F02, F11, F12, F13. Основа A06.

**Работы**

- Ввести единый слой операций над пользовательскими данными. Источники истины, резервные копии и миграции должны быть явными; чтение устаревшей копии заметки не должно побеждать более новую IndexedDB-запись.
- Перестать перезаписывать всё состояние устаревшим объектом вкладки. Обновлять отдельные ключи/записи транзакционно, передавать изменения другим вкладкам через поддерживаемый межвкладочный канал и разрешать конфликты детерминированно.
- Для одновременного редактирования одной заметки обнаруживать конфликт и не терять несохранённый текст молча. Для разных уроков и закладок изменения из обеих вкладок должны объединяться.
- Обрабатывать запрет localStorage, недоступную IndexedDB, quota и прерывание операции. В ограниченном режиме оставить чтение сайта и временное состояние, ясно сообщать, что оно не сохранено надёжно.
- Сделать импорт двух версий staged/атомарным: проверить весь файл и ID до изменения данных, сохранить прежнее состояние до успешного commit, корректно откатить неудачу. Ошибка записи заметки не должна скрываться.
- Ввести достоверные состояния заметки: редактируется/сохраняется/сохранено/не сохранено/ошибка. При сбое оставить вводимый текст доступным для копирования или экспорта; подтверждать успех только после подтверждённой записи.

**Проверки и выход**

- Два реальных браузерных контекста одновременно меняют разные статусы и закладки; все изменения видны без перезагрузки и сохраняются после неё.
- Конкурентная правка одной заметки вызывает понятное разрешение конфликта; блокировка хранилищ, quota, закрытие вкладки во время импорта и ошибка на середине не уничтожают прежний backup и не показывают ложный успех.
- v1/v2 импорт, экспорт, очистка и прежние миграции покрыты проверками; пользовательские ответы не отправляются на внешний сервер.

- Для любого значимого текста проверить контраст WCAG AA в обеих темах. Не использовать `#888` на белом для обычного мелкого текста, даже если он назван caption в исходном контракте.

**Адаптивная работа**

**Новый логотип и favicon — обязательный scope**

- Использовать корневой исходник `Sales OS Stepped Logo.png` как логотип Sales OS в каждом месте сайта, где сейчас показывается старый текстовый/графический знак: Astro Shell, desktop sidebar, mobile header/drawer, Python fallback shell и других реально публикуемых шаблонах. Если `legacy-index.html` остаётся доступной точкой входа, обновить и её; если нет — явно исключить её из публикации.

- Не растягивать изображения и не обрезать сам знак. У исходного логотипа большие прозрачные поля: подготовить оптимизированную копию с обрезкой только прозрачных отступов, сохранить пропорции и прозрачность. Для компактного мобильного места допустима отдельная версия только со ступенчатым знаком из этого же исходника; рядом сохранить доступное имя Sales OS.

Favicon исходник почти квадратный, поэтому вписать его целиком в квадрат, не обрезая ступени. Использовать PNG/ICO, а SVG — только если он является корректным отдельным векторным ресурсом, не имитацией трассировки растрового PNG.

Для тёмной темы использовать светлый вариант, полученный из того же знака, или эквивалентную CSS-маску/фильтр. Для браузерной вкладки и PWA-манифеста задать корректные PNG/ICO/SVG ссылки и, если требуется, вариант по color scheme; favicon обязан оставаться различимым на светлой и тёмной полосе вкладок.
- Не менять и не перезаписывать оригиналы в корне проекта. Не заменять ими только Astro-версию, забывая fallback и офлайн-выход.

**Приёмка:** скриншоты 320/390/768/1024/1440 px в light/dark для основных шаблонов; все практики не вызывают page-level overflow. Логотип нигде не искажён, читаем, а favicon виден в реальной вкладке. Повторно проверить Contrast, keyboard focus, длинные тексты и крупный текст браузера.

- Вводить структурированные поля и ссылки без нестабильных ID и разрушения старых экспортов; обеспечить валидацию источников и понятное отображение неполных материалов.

**Редакторская приёмка F33 / A08**

- Создать проверяемую карту утверждение → первичный/надёжный источник → дата и scope проверки → статус и ответственный редактор. Отдельно помечать изменчивые нормы права и правила платформ.
- Проверить связи источников с конкретными тезисами и материалами: одна общая ссылка не должна создавать ложное впечатление, что сотни уроков независимо подтверждены.
- Не снимать `editorial_draft` массово скриптом. Менять статус только при наличии редакторской записи. Полноценную фактологическую и юридическую приёмку нельзя подтвердить только сборкой или языковой моделью; для неё нужен профильный рецензент.
- Сделать видимую карту готовности корпуса: какие из 430 учебных документов проверены, какие ожидают рецензента и на какую дату рассчитана проверка. Редакторский gate считается закрытым только после зафиксированной проверки всех 430 документов с источниками, статусом и ответственным рецензентом; право и быстро меняющиеся правила платформ требуют профильной проверки. Если рецензент недоступен, оставить статусы draft и явно держать этот gate открытым; независимые технические milestones можно продолжать.

**Приёмка M5 приложения:** все 22 интегрирующие главы читаются; 3 библиотеки доступны из приложения; общие шаблонные рекомендации заменены предметными во всех 336 уроках; все 72 задания имеют подходящие критерии; пользователь не получает неверное «продолжить»; каждый документ имеет честный, проверяемый редакционный статус. Статус `verified` означает наличие записи проверки, не просто прохождение lint. Отдельный **редакторский gate M5-CONTENT** закрывается только после документированной рецензии всех 430 материалов; без неё приложение может быть технически готовым, но курс не объявляется полностью проверенным.

## M6 — Полный поиск и надёжный офлайн-режим

**Аудит:** F03, F14–F17. Возможности A04 и A07.

**Работы**

- Явно определить состав индекса: весь пользовательский корпус материалов (теория, упражнения, главы модулей, итоговый проект, библиотеки и источники в согласованном объёме), а не разные случайные наборы для Pagefind и JSON fallback.
- Включить поиск по согласованному корпусу и фильтры по уровню, модулю и типу материала. Ошибка Pagefind после инициализации запускает доступный fallback; сбой индекса показывается как ошибка с действием восстановления, а не нулевой результат.
- Расширенный поиск по закладкам и заметкам выполнять локально в браузере; не передавать частные записи Pagefind/CDN, телеметрии или backend.
- Исправить формирование offline URL для Windows и POSIX. Версия кэша должна меняться при изменении фактических CSS, JS, HTML, контента, manifest и поисковых ресурсов; безопасно очищать только устаревшие кэши своего приложения.
- Установку offline-пакета сделать наблюдаемой и восстанавливаемой: сохранять статус, дату/версию и результат; сообщать о частичных ошибках с перечнем ресурсов; позволять повторить или отменить задачу; после удаления сразу отражать актуальное состояние.
- Расширить интерфейс менеджера offline-пакета (A07): показывать примерный объём, доступные модули, версию и действия обновления/повтора. Не обещать офлайн-доступ к тому, чего браузер фактически не закэшировал.

**Приёмка**

- Offline install успешно получает все manifest URL на Windows и Linux; URL — валидные относительные веб-пути с `/`, без `dist\\` и локальных путей.
- Установленный пакет открывает все core routes, CSS/JS, поиск и нужный учебный контент после отключения сети и reload. Заметки и прогресс остаются доступны локально.
- Симулировать отказ сетевого фрагмента Pagefind, плохой ресурс offline, отмену, повтор, частичную загрузку, quota и смену версии; каждая ситуация имеет правдивый статус и не подменяется пустой выдачей.
- Проверить реальные сервис-воркеры и браузерные URL E2E, а не только содержание JSON-манифеста.

## M7 — Завершённые практические инструменты

**Аудит:** продуктовые продолжения после устранения базовых дефектов. Возможности A02, A05, расширение A06.

- Добавить структурированную форму ответа к практикам, связанную с индивидуальными критериями M5. Поддержать сохранение черновика, самооценку, повторную итерацию и историю; не выставлять баллы, которые пользователь трактует как внешнюю аттестацию.
- Добавить ненавязчивую очередь повторения (A05): пользователь сам выбирает «вернуться позже», видит due items и короткие вопросы активного воспроизведения. Не строить streaks, давление или игровые баллы без подтверждённой учебной ценности.
- Дополнить настройки центром резервных копий (A06): дата и размер последнего экспорта, preview содержимого импорта, выбор merge/replace с ясными последствиями, восстановление предыдущей копии и обозначение локальности/происхождения данных.
- Проверить связь этих инструментов с уже реализованной моделью хранения, миграциями и offline-пакетом. Никакая функция не должна создавать второй несогласованный источник user data.

**Приёмка:** структурированные ответы, история, очередь повтора и preview backup переживают reload, экспорт, импорт, отказ хранилища и работу нескольких вкладок. Merge не дублирует и не стирает незатронутые записи; replace требует ясного подтверждения и имеет восстановимую точку возврата.

## M8 — Сквозная приёмка, производительность и готовность релиза

**Аудит:** F39–F40, итоговая повторная проверка всех F01–F38 и A01–A08.

**Полный release gate**

- Чистая установка и production build на Windows/Linux проходят без сетевых workaround и побочных генераций. Vercel preview показывает артефакт, собранный из текущего commit. Локальная Python fallback-сборка отдельно запускается и проверяется.
- Для всех маршрутов, генерируемых manifest (baseline аудита — 475 URL), проверить ожидаемые ответы, уникальность H1, внутренние ссылки, страницу 404 и отсутствие browser page errors. Число маршрутов получать из актуального manifest, не закреплять противоречивое число в тесте.
- Для всех 13 семейств страниц пройти фактические light/dark screenshots при 320, 390, 768, 1024 и 1440 px; длинные страницы и все 72 упражнения дополнительно проверить на 320/390 px. Использовать audit screenshots как сравнимую исходную точку и обновлять их при принятом дизайне.
- Пройти реальные E2E потоки навигации, progress, заметки, export/import v1/v2, конфликт вкладок, storage-denied/quota, поиск/его fallback, mobile drawer клавиатурой, offline install/update/offline reload, final-project journey и оба layout themes.
- Выполнить keyboard-only проверку, NVDA на Windows и проверку увеличения браузера до 200%; проверить цветовой контраст, имена, роли, фокус, touch targets и reduced motion. Результаты описывать по конкретным применимым критериям, не заявлять сторонний WCAG-сертификат без аудита.
- Повторно измерить transfer size и время загрузки. Убрать React runtime главной, если три статических счётчика могут использовать существующий progress API без клиентского бандла; тяжёлый JSON fallback не скачивать при обычном открытии страницы, если поиск ещё не нужен. Сохранять цифры до/после и не выдавать размер bundle за Lighthouse/real-device результат.
- Для F40 ввести осмысленные описания страниц, canonical/Open Graph только там, где публичная индексация уместна, согласовать версию package/UI и проверить app-404. Проверить favicon и logo assets в полном build и offline-кэше.
- Обновить README, ARCHITECTURE, DESIGN_COMPLIANCE, QA_REPORT, локальный Windows verification guide, MILESTONE_LOG и этот roadmap по фактическому результату. Каждая незавершённая редакторская проверка остаётся явно отмеченной.

**Приёмка релиза:** нет открытых воспроизведённых блокеров P1; каждый P2 устранён либо имеет явное продуктовое решение и тестируемое ограничение; P3 оптимизации измерены и приняты на основании данных. Все инженерные milestones имеют фактический PASS. Заявление «полный учебный курс проверен» допустимо только после PASS отдельного gate M5-CONTENT; иначе в итоговом статусе явно остаётся незавершённая редакционная приёмка. Публикация в production в этот scope не входит — проверяется preview и готовая поставка.
