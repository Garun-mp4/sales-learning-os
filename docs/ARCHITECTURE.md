# Архитектура Sales OS

Sales OS — статическая русскоязычная обучающая платформа без backend и учётных записей. Исходные Markdown и устойчивые ID хранятся в `sales-knowledge-base/`; браузерные данные пользователя остаются на устройстве. Инженерная self-review не является сертификацией, а статус материала `editorial_draft` не снимается сборкой или тестом.

## Источники и сборки

- `scripts/audit.py` проверяет исходный курс и создаёт `src/generated/content-manifest.json` и клиентский индекс.
- `src/content.config.ts` подключает Astro Content Collection напрямую к `sales-knowledge-base/modules/`; курс не копируется в параллельное дерево.
- `sales-knowledge-base/editorial-review-ledger.json` хранит проверки отдельных тезисов; `scripts/audit.py` сверяет записи с ID документов и источников и не допускает статуса `verified` без полной проверки. `/editorial-review/` показывает карту состояния корпуса, а правила работы с реестром находятся в `sales-knowledge-base/EDITORIAL_REVIEW_WORKFLOW.md`.
- `sales-knowledge-base/GLOSSARY.md`, `CASE_LIBRARY.md` и `TEMPLATE_LIBRARY.md` доступны как исходные документы коллекции на маршрутах `/library/`; связанная библиотека предлагается из релевантных материалов. Поиск индексирует их наряду с курсом.
- `scripts/prepare_astro.py` создаёт общий JSON search corpus из 467 документов (430 учебных материалов, 3 библиотеки, итоговый проект и 33 источника), runtime-ассеты и очищенный снимок итогового проекта из исходников. Он не строит второй сайт перед Astro.
- Astro 7 собирает production-сайт из `src/pages/`, `src/layouts/`, компонентов, стилей и исходной коллекции. Pagefind индексирует тот же корпус и три фильтра (`level`, `module`, `kind`); JSON fallback сохраняет совместимую классификацию. Личные заметки, ответы, проекты, закладки и шаблоны присоединяются только по явному запросу браузера и не включаются в публичный индекс или URL.
- `scripts/after-build.mjs` перечисляет фактически собранные production-файлы с canonical URLs и размерами, рассчитывает версию по содержимому output и записывает schema-2 offline manifest в `dist/`. `scripts/service-worker.js` обслуживает same-origin network-first запросы, но использует только кэш, у которого готовность подтверждена version marker. Незавершённые установки не активируются как полные пакеты.
- `dist/` — одноразовый, игнорируемый результат Astro. Python fallback запускается явно через `python scripts/build.py --out-dir dist-fallback`; он не очищает и не подменяет Astro output.
- Vercel выполняет `npm ci`, создаёт `.venv` для `requirements.txt`, запускает `npm run build` с `.venv/bin` в `PATH` и публикует `dist/`. Изолированное окружение обходится без установки пакетов в управляемый системный Python. В репозитории нет сохранённых сборочных HTML-страниц.

## Runtime и границы данных

M2 добавляет `trainer-core.js` (контракт графов и снимков, загружается перед user-store) и `trainer.js` (только страницы `/trainer/`). Публичные сценарии находятся в `sales-knowledge-base/trainer-scenarios.json`; `scripts/trainer_content.py` проверяет графы/ссылки и формирует одинаковый HTML для Astro и Python fallback. Личные сессии входят в единый объект состояния и актуальный backup v8 (v4 в исходной поставке M2); схема IndexedDB остаётся v3. UI не анализирует смысл свободного текста: переход определяется выбранным действием, разбор — его сохранённым объяснением. История не индексируется публично.

`src/scripts/user-store.js` — единственный runtime-слой пользовательских данных: IndexedDB (`sales-os-personal`, schema v3) является основным хранилищем состояния, заметок и точек восстановления; отдельные транзакции, ревизии заметок и generation защищают от потерянных обновлений. localStorage используется для миграционных снимков и явно ограниченного режима. Межвкладочные обновления синхронизируются, импорт backup v1–v8 валидируется до атомарной замены, экспорт остаётся локальным JSON `sales-os-v8`. `src/scripts/app.js` подключает API к интерфейсу, обслуживает публичный поиск, явный локальный поиск заметок/закладок/проектов/шаблонов, offline package и PWA worker; главная обновляет прогресс через vanilla-JS подписку без React hydration. Менеджер хранит статус офлайн-загрузки отдельно в localStorage, умеет повторить/отменить задачу и удаляет только кэши `sales-os-offline-*`. Данные пользователя и поисковый запрос не отправляются на сервер приложения.

Общая оболочка и sidebar находятся в `src/layouts/Shell.astro`; UI-атомы и course routes — в `src/components/` и `src/pages/`. Дизайн-токены, responsive layout и темы определены в `src/styles/app.css`. `DESIGN-vercel.md` — визуальный контракт: нейтральные поверхности, ограниченная палитра, ясная типографика, разделители вместо декоративных эффектов, accessible focus и уважение к reduced motion.

## Подготовка и локальные команды

```powershell
py -m pip install -r requirements-dev.txt
npm ci
npm run dev
```

`dev`, `check`, `lint` и `build` готовят небольшие производные входы; они не запускают Python site renderer и не создают промежуточный сайт в `dist/`. `dev` и `build` сбрасывают Astro content cache перед запуском: изменившийся Markdown renderer/plugin не должен незаметно оставить старый HTML в существующей рабочей копии. Content Collection загружает один и тот же исходник напрямую, а Astro и fallback используют разные outputs. Канонические проверки:

```powershell
npm run lint
npm run check
npm run build
npm run test:quality
npm run test:e2e
npm run test:fallback
```

CI выполняет эти проверки на Windows и Linux. Playwright Node и Python pinned на совместимые версии, браузер устанавливается один раз для общей browser cache.

Production preview проверяется на собранной Astro-версии:

```powershell
npm run build
# В первом терминале:
npm run preview -- --host 127.0.0.1 --port 4321 --strictPort
# Во втором терминале:
$env:PLAYWRIGHT_BASE_URL = "http://127.0.0.1:4321"
npm run test:preview
```

`test:preview` проверяет Pagefind и offline install в Chromium, все manifest-маршруты, privacy/SEO-метаданные, reflow при ширине 640 CSS px и screenshot-матрицу 21 representative route × 5 ширин × 2 темы.

## Проверяемые риски

`docs/MILESTONE_LOG.md` содержит датированные результаты и различает успешно выполненные проверки, заблокированные окружением действия и редакционные зависимости. ## M3: сохранённое занятие

today-core.js валидирует настройки и снимки, составляет план детерминированно по статусам и ручной очереди, выбирает замену без повторения. Загружается перед user-store на каждой странице. today.js работает только на /today/, изменяет план атомарным updateState по актуальному состоянию. Разные пункты из разных вкладок сохраняются; устаревшее действие по заменённому/завершённому пункту отклоняется. Сроки очереди и статусы курса не изменяются.

today_content.py формирует одинаковую разметку обеих сборок; главная содержит выбор времени/цели и переход к сохранённым занятиям. Время — явно приблизительные авторские диапазоны отдельных шагов. День локальный, пояс хранится в снимке. Полночь/смена пояса только показывают уведомление. Нет обязательного таймера, долга, streak или скрытой аналитики.

## M4: проверка понимания

`knowledge-core.js` загружается перед user-store: отдельный блок knowledgeReview, снимки вопросов, объективные ключи/самооценка, идемпотентная отправка, CAS черновиков, opt-in расписание v1. `knowledge.js` работает на `/review/check/`; `knowledge_content.py` формирует одинаковый реестр и HTML Astro/fallback. `priorityForToday` передаёт добровольные наступившие вопросы в M3 через явные ссылки; старые планы остаются снимками. Статусы освоения не меняются. Подробности: [M4_KNOWLEDGE_REVIEW.md](M4_KNOWLEDGE_REVIEW.md).


## M5: личные проекты

`projects-core.js` загружается до user-store и владеет проектами, ревизиями контекста/этапов, снимками практики, миграцией и безопасным экспортом. `projects.js` работает на `/projects/`, переиспользует существующий PracticeWorkspace через адаптер хранения в `app.js`; редактор и его обработка конкурентных черновиков общие. Проекты хранятся отдельно от `practiceDrafts.FINAL_PROJECT`, поэтому переключение не подменяет ответы. `projects_content.py` извлекает исходные десять критериев и формирует одинаковый каркас Astro/fallback.

Backup v7 переносит проекты; IndexedDB остаётся schema v3. Старый итоговый проект и заметка копируются в «Мой первый проект» без удаления исходников. Импорт отличающейся версии проекта сохраняет отдельный вариант; tombstones предотвращают воскрешение окончательно удалённых проектов при merge. При конфликте контекста UI сохраняет локальную форму и предлагает скачать её или явно загрузить сохранённый вариант. Личный поиск включается пользователем; публичный Pagefind личных данных не получает. Подробности: [M5_PROJECT_WORKBOOK.md](M5_PROJECT_WORKBOOK.md).

## M6: личные шаблоны

`templates-core.js` загружается до user-store, валидирует личную библиотеку и безопасно подставляет только `service`, `client`, `context` и `next_step`. Исходник хранится отдельным снимком; именованные версии неизменяемы, восстановление сохраняет предыдущий текст, архив сохраняет карточку и историю. `templates.js` работает только на `/library/templates/`, читает поля выбранной тетради M5 для предпросмотра без записи обратно в проект и предоставляет ручной fallback при запрете Clipboard API. Каталог и его статические стартовые тексты помечены `data-pagefind-ignore`; частный поиск собирает тексты только после явного включения локального поиска.

`sales-knowledge-base/personal-template-starters.json` — единственный источник пяти редактируемых стартовых текстов; `scripts/template_content.py` валидирует категории, переменные и маркировку, а Astro и fallback используют общий HTML каркас менеджера. Backup v8 добавляет шаблоны и их архив/версии; импорт v1–v7 оставляет для нового раздела пустое состояние. Новые поля помещаются в общий state в IndexedDB schema v3, миграция таблиц не требуется. Подробности: [M6_TEMPLATE_LIBRARY.md](M6_TEMPLATE_LIBRARY.md).
