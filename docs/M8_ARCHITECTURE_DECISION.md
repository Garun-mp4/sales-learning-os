# M8 — синхронизация между устройствами: архитектурное решение

Дата: 10 октября 2026. Статус: **архитектурная подготовка; облачный сервис не подключён, M8 не принят**.

## Проверенное состояние проекта

- Production-приложение собирается в статический Astro `dist/`; `vercel.json` задаёт статический output. `output: "static"` включён в `astro.config.mjs`. Полный переход сайта на SSR для синхронизации не нужен.
- В репозитории нет Supabase/Neon/Auth SDK, API-обработчиков, локальной `.vercel`-привязки или `.env*`-файлов. Vercel CLI на этой машине не обнаружен. Текущая сессия компьютерного браузера не показывает открытых вкладок, через которые можно проверить авторизованный dashboard.
- Личные данные пока лежат в IndexedDB/localStorage одного локального пространства. IndexedDB — schema v3; экспорт — `sales-os-v9`. Durable cloud outbox, аккаунты и изоляция данных между аккаунтами не реализованы.
- В существующем merge резервной копии уже есть полезные доменные правила, но они сами по себе не являются протоколом синхронизации и не заменяют серверную конкурентную проверку.

## Рекомендация к подтверждению

Использовать **Supabase Auth + PostgreSQL через Vercel Marketplace**, сохранив статические Astro и Python fallback-сборки. Supabase объединяет Auth и Postgres; Vercel Marketplace создаёт интеграцию и синхронизирует настройки окружений с проектом. Доступ к данным из браузера возможен только через publishable key и Supabase Data API с обязательным Row Level Security (RLS); секретный/service-role key не попадёт в клиентскую сборку. [Интеграция Supabase с Vercel](https://vercel.com/marketplace/supabase/supabase), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

Для входа предлагается email OTP. Текущий встроенный почтовый провайдер Supabase ограничен двумя письмами в час на проект; для обычного production-использования следует подключить отдельный SMTP. Один email можно повторно запросить через 60 секунд; код по умолчанию действует один час. [Лимиты Auth](https://supabase.com/docs/guides/auth/rate-limits), [вход без пароля](https://supabase.com/docs/guides/auth/auth-email-passwordless).

Astro останется статическим. Клиент будет отправлять аутентифицированные операции в Supabase Data API; проверка владельца и атомарная смена серверной ревизии выполняются PostgreSQL-функцией через `rpc()`, с RLS и серверной валидацией. Для функций БД Supabase рекомендует `SECURITY INVOKER`; при необходимости привилегированного удаления аккаунта отдельная серверная функция должна использовать секрет только на сервере. [Функции PostgreSQL](https://supabase.com/docs/guides/database/functions).

## Стоимость, регион и восстановление

- Supabase Free сейчас стоит $0, но проекты без активности приостанавливаются через неделю; квота включает 500 MB базы и 5 GB исходящего трафика. Этот план годится для интеграционной проверки, но не для постоянно доступной production-синхронизации.
- Supabase Pro начинается с $25 в месяц; на странице тарифа указаны 100 000 MAU, 8 GB на проект, дневные резервные копии с 7-дневным хранением и $10 compute credits, покрывающие один Micro-инстанс. Дополнительное потребление может увеличить счёт. Семидневный PITR сейчас отдельно оценивается примерно в $100 в месяц; включать его без отдельного бюджета не предлагается. Текущие цифры нужно повторно проверить при создании ресурса. [Официальные цены Supabase](https://supabase.com/pricing), [цены PITR](https://supabase.com/docs/guides/platform/manage-your-usage/point-in-time-recovery).
- Проект имеет один основной регион, который определяет расположение primary data. Кандидат — `eu-central-1` (Frankfurt), если аудитория и требования к хранению это допускают. Регион следует выбрать по целевой аудитории и требованиям владельца; географический регион сам по себе не подтверждает юридическое соответствие. [Список регионов](https://supabase.com/docs/guides/platform/regions).
- Резервное восстановление должно быть испытано до PASS. Дневные копии Pro подходят как базовый механизм; PITR — опциональный отдельный расход, а не часть обещания M8.

## Протокол, который предстоит реализовать

1. Локальный режим остаётся доступным без аккаунта. До первой загрузки показать состав локальных данных, категории и объём; создать восстанавливаемую локальную точку и попросить явное подтверждение. Начальное объединение не должно молча перезаписывать ни одну сторону.
2. Каждое сохранённое изменение, когда аккаунт подключён, атомарно добавляется в durable IndexedDB outbox вместе с локальной записью. Операция получает UUID и локальную ревизию; ответ сервера подтверждается cursor/revision. Повтор UUID после таймаута возвращает прежний результат и не создаёт дублей.
3. Сервер хранит монотонную ревизию и применяет пакет только при ожидаемой базовой ревизии. Устаревший пакет получает конфликт и актуальные данные; клиент объединяет домены по явным правилам и повторяет запись на новой ревизии. Часы устройства не решают конфликт сами.
4. Истории ответов объединяются по ID; одновременно изменённые тексты и версии сохраняются отдельно. Статусы, очередь повторов и явный reset получают собственные правила и разрешение конфликтов. Удаления сохраняются как tombstones; отключённое старое устройство обязано сначала забрать tombstones или заново связать локальную копию через preview.
5. Локальное хранилище разделяется по аккаунту ещё до отображения данных. Смена аккаунта не использует прежний outbox. При выходе пользователь выбирает, оставить ли локальную копию аккаунта на этом устройстве или удалить её; следующий пользователь открывает своё пустое/гостевое пространство.
6. UI показывает только локальный режим, очередь, синхронизацию, offline, конфликт, истёкшую сессию и последнюю успешную доставку. Истечение сессии не очищает outbox. Auth callback и личные ответы не попадают в общий offline-кеш; тексты пользователя не пишутся в серверные логи.
7. Экспорт остаётся доступен независимо от облака; удаление облачных данных и аккаунта проверяется отдельно. Добавить тестовые и production-проекты, SQL migrations/RLS тесты, лимиты размера и частоты, процедуру восстановления и безопасный rollback схемы.

## Gate перед интеграцией и приёмкой

В текущем проекте нет облачного проекта или локальной привязки Vercel. Поэтому невозможно проверить авторизацию, RLS, работу двух реальных browser contexts, offline-догон, изоляцию двух аккаунтов, backup/restore облака либо production smoke. Демонстрационный/mock backend не закроет M8 и не будет выдаваться за синхронизацию.

Для продолжения нужны: подтверждение провайдера и ежемесячного лимита расходов; регион хранения и аудитория; email/SMTP-провайдер или OAuth-решение; доступ к связанному Vercel-проекту и разрешение создать соответствующий ресурс. После этого можно автоматизировать всё, что поддерживается аккаунтом, не передавая секреты в чат.

До внешней интеграции M8 остаётся **IN PROGRESS**, а не PASS. Приёмка включает два независимых устройства, запись offline/повтор после обрыва, идемпотентность, истечение сессии, конфликт одновременной правки и reset, две учётные записи, прямой API-запрос к чужим данным, logout, экспорт/удаление, реальный backup/restore и production smoke.
