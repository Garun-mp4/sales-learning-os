# Sales OS: план восьми продуктовых milestones

Дата: 9 октября 2026. Статус: **M1 и M2 реализованы технически; независимая редакционная приёмка открыта. M3–M8 не начаты**.

Цель: превратить существующий курс в последовательный цикл «изучить → вспомнить → потренироваться → получить обратную связь → применить в проекте». Сохранить простоту интерфейса, Vercel-дизайн и возможность работать локально без аккаунта.

Документ дополняет `IMPLEMENTATION_ROADMAP.md`, а не заменяет его. Старый roadmap описывает техническую готовность; этот — восемь новых продуктовых возможностей. Наличие фич не считается доказательством эффективности обучения или экспертной проверки содержания.

## Исходное состояние

- Astro формирует статические страницы; Pagefind и JSON fallback обеспечивают поиск. Резервный Python renderer существует отдельно.
- Уже есть 336 уроков, 72 практики, справочники, заметки, закладки, история итераций, ручная очередь повторения и полный offline-пакет.
- `PracticeWorkspace.astro` обслуживает практики и десять этапов итогового проекта. Не создавать вместо него второй независимый редактор.
- `src/scripts/user-store.js` — единый слой IndexedDB-first данных. После M2 текущий backup — `sales-os-v4`; предусмотрен импорт v1/v2/v3/v4. Межвкладочная синхронизация уже есть, межустройственной нет.
- Учебные материалы имеют редакционный статус. Новые примеры, сценарии и ответы должны проходить отдельную содержательную проверку.
- Backend, аккаунты, автоматическая облачная синхронизация и AI-проверка сейчас отсутствуют.

## Порядок и самостоятельность

Нумерация соответствует восьми обсуждённым идеям. Рекомендуемая очередь реализации: **M1 → M5 → M3 → M4 → M2 → M6 → M7 → M8**. Сначала обратная связь и применение, затем организация занятий, проверка знаний и новые инструменты.

Каждый milestone должен выпускаться отдельно и работать без незавершённых следующих этапов. Между завершёнными фичами допускаются интеграции; отсутствие другой фичи не должно оставлять пустые кнопки, сломанные ссылки или блокировать сценарий.

| Milestone | Результат | Зависимость | Относительная сложность |
| --- | --- | --- | --- |
| M1 | Разобранные ответы и обратная связь | Существующая практика | Средняя разработка, высокая редакционная работа |
| M2 | Тренажёр переписки | Самостоятельные сценарии; использует критерии M1, если они готовы | Высокая |
| M3 | Занятие на сегодня | Текущие статусы, практика и ручная очередь | Средняя |
| M4 | Повторение с проверкой понимания | Существующая очередь; интеграция с M3 необязательна | Средняя разработка, высокая редакционная работа |
| M5 | Рабочая тетрадь проекта | Текущий итоговый проект | Средняя–высокая |
| M6 | Личная библиотека заготовок | Существующий справочник шаблонов | Средняя |
| M7 | Выделения и привязанные заметки | Существующие статьи и заметки | Средняя–высокая |
| M8 | Синхронизация устройств | Завершённые модели M1–M7 и облачная инфраструктура | Высокая |

Сложность — сравнительная оценка, не обещание сроков. Перед началом каждого этапа уточнить объём по реальным данным и разбить его на небольшие проверяемые задачи.

## Общий контракт реализации

1. **Дизайн.** Следовать `DESIGN-vercel.md`: существующие токены, Geist, нейтральные поверхности, общие контролы и SVG Lucide. Сохранять светлую/тёмную темы, клавиатуру, видимый focus, reduced motion и доступные подписи. Основные сценарии проверять на 320, 390, 768 и 1440 CSS px.
2. **Границы кода.** Сохранить Astro, единый user-store и исходный курс. Новые крупные возможности выносить в небольшие тематические runtime-модули, подключаемые на нужных страницах; не увеличивать бесконечно `app.js`. Не вводить новый frontend framework ради этих фич.
3. **Контент.** У публичных сущностей должны быть устойчивые ID, версия, связи с материалами и статус проверки. Все ссылки и схемы проверяются при сборке. Пользовательские данные не попадают в публичный индекс или сборочные файлы.
4. **Данные.** Перед каждым расширением описать схему, лимиты, импорт, экспорт, объединение и восстановление. Версию IndexedDB и формат backup повышать только при необходимости, отдельно друг от друга. Старые копии импортируются без потери существующих полей. Неподдерживаемые будущие форматы отклоняются с объяснением, а не молча обрезаются.
5. **Сохранность.** Для новых записей использовать устойчивые ID; изменения сохранять транзакционно. Обрабатывать несколько вкладок, квоту, недоступное хранилище и незавершённое сохранение. Не перезаписывать конфликтующие ответы без восстановления.
6. **Offline.** M1–M7 должны работать после установки полного пакета. Новые публичные ресурсы включаются в manifest; частные данные остаются в user-store. M8 расширяет локальную работу и не делает вход обязательным.
7. **Обе сборки.** Astro и Python fallback читают одинаковые публичные данные и поддерживают одинаковые локальные сценарии. Облачная часть M8 развёртывается отдельно; fallback сохраняет локальные фичи и явно показывает доступность облака.
8. **Состояния.** Для каждого экрана предусмотреть загрузку, пустое состояние, ошибку с повтором, сохранение, успех, недоступную возможность и восстановление после перезагрузки. Скрытые незавершённые возможности не выдавать за готовые.
9. **Проверка.** Для изменений хранилища обязательны миграционные и recovery-тесты; для пользовательских потоков — браузерные проверки. Не заменять содержательную проверку тестами наличия кнопок.
10. **Поставка.** После проверки — отдельный понятный commit, push в `origin/main`, проверка deployment и основного production-сценария. Фиксировать результаты, ограничения и незакрытые пункты в этом документе. Статус milestone: `не начат → в работе → проверка → завершён`.

## M1. Разобранные примеры и обратная связь

**Статус на 2026-10-09:** инженерная проверка Astro и Python fallback пройдена. Независимая редакционная проверка и пользовательская проверка пользы остаются открытыми. [Отчёт и условия полной приёмки](M1_PRACTICE_FEEDBACK.md).

**Результат:** пользователь понимает, почему ответ удачен или слаб, и может целенаправленно улучшить следующую итерацию.

### Объём

- Подготовить полный набор разборов для 10 практик первого выпуска. При выборе покрыть исследование клиента, первое сообщение, discovery, оффер, возражение и переговоры; перед реализацией зафиксировать точные ID.
- Для каждой: слабый, приемлемый и сильный пример; объяснение по существующим критериям; типичные ошибки; последовательные подсказки; несколько допустимых подходов, если нет единственного правильного ответа.
- Все 72 практики сохраняют полноценный текущий редактор. Для остальных честно указывать отсутствие готового разбора; не генерировать фиктивные эталоны.
- Добавить режим сравнения двух сохранённых итераций по критериям: ответы, самооценка, дата, следующий шаг. Сравнение доступно всем практикам и итоговому проекту.
- Открытие примеров — по действию пользователя. Разрешить посмотреть их до ответа, но объяснить пользу самостоятельной попытки; не вводить жёсткую блокировку.

### Реализация

- Создать версионируемый публичный реестр разборов, связанный с ID практики и ID критериев. Использовать редакционный workflow; проверять несовпадения рубрик при сборке.
- Расширить `PracticeWorkspace.astro` переиспользуемыми блоками подсказок и сравнением; исходные снимки истории остаются неизменными.
- В личных данных при необходимости хранить только состояние раскрытия и ссылки на выбранные итерации. Просмотр примера не повышает статус владения навыком.
- Не внедрять автоматическую оценку свободного текста по ключевым словам. Не выдавать самооценку или сравнение с примером за внешнюю экспертизу.

### Приёмка

- Все 10 разборов проверены по содержанию и связаны с реальными рубриками; статус проверки виден.
- Путь «ответ → сохранить → открыть разбор → улучшить → сравнить» проходит после reload и офлайн.
- Сравнение корректно показывает пустой ответ, длинный текст и изменённую между версиями рубрику.
- Регрессия: история и backup старых практик сохранены; раскрытие подсказок доступно с клавиатуры на mobile/desktop.

**Проверка пользы:** в небольшом пользовательском тесте человек может объяснить, что именно улучшил и на какой критерий опирался. Дополнительно считать долю вторых итераций локально; сам факт второй попытки не считать улучшением качества.

## M2. Тренажёр переписки с клиентом

**Статус на 2026-10-09:** техническая реализация и проверка обеих сборок завершены. Независимый просмотр сценариев редактором и пользовательская проверка переноса навыка остаются открытыми. [Объём, данные и приёмка M2](M2_CONVERSATION_TRAINER.md).

**Результат:** пользователь отрабатывает решения в диалоге и получает объяснимый разбор последствий.

### Объём

- Первая законченная версия: минимум 6 сценариев — цена без контекста, «дорого», молчание после предложения, сравнение с конкурентом, неопределённая потребность, бесплатная дополнительная работа.
- В каждом: контекст услуги и клиента, цель, ограничения, не менее 3 содержательных точек выбора и несколько исходов. Никакой гарантии сделки за «правильную» реплику.
- Поле собственного ответа и выбор намерения/действия. В детерминированной версии ветка определяется явным выбором действия; свободный текст сохраняется для саморазбора, но система не притворяется, что понимает его автоматически.
- После завершения: история диалога, сильные решения, упущения, ссылки на курс и предложение повторить другой подход. Можно завершить диалог корректным отказом.
- Сохранение и продолжение незавершённой сессии, история попыток и удаление выбранной сессии с восстановлением.

### Реализация

- Отдельный раздел тренажёра, каталог и экран сценария. Сценарии — публичные графы с устойчивыми ID узлов, переходов, версией и редакционным статусом.
- Валидатор графа: недостижимые узлы, отсутствующие переходы, неконтролируемые циклы, отсутствие конечного состояния. Сценарные ответы — безопасный текст, без выполнения HTML.
- Личная сессия хранит версию сценария, пройденные узлы, выбранные действия, тексты и итог. При обновлении сценария завершённая история остаётся читаемой; несовместимая активная попытка сохраняется и предлагает начать новую.
- Сценарии и движок работают офлайн; результаты входят в backup и последующую синхронизацию.
- AI не входит в критерий готовности M2. Его будущая версия требует отдельного плана API, стоимости, приватности и проверки качества; она не должна задерживать выпуск законченного сценарного тренажёра.

### Приёмка

- Все ветки шести сценариев проверены автоматически и просмотрены редактором; разбор соответствует выбранным действиям.
- Путь «начать → ответить → закрыть → продолжить → завершить → сравнить попытки» работает онлайн/офлайн.
- Повторное нажатие и reload не создают лишних сообщений; пользователь может исправить черновик до отправки.
- В интерфейсе явно объяснена роль собственного текста и выбора действия; нет ложной AI-оценки.

**Проверка пользы:** сравнивать решения в повторной попытке и новом похожем кейсе по человеческой рубрике, а не только рост внутреннего балла.

## M3. Режим «Занятие на сегодня»

**Результат:** пользователь получает посильный план и начинает работу без самостоятельного перебора сотен материалов.

### Объём

- На главной: «Начать занятие», выбор 10/20/40 минут и текущей цели. Цель можно пропустить или изменить; обязательного onboarding нет.
- План включает небольшую комбинацию повторения, нового материала и шага практики. Показывать основание каждого пункта и приблизительность длительности.
- Можно заменить пункт, пропустить, поставить паузу и продолжить на том же месте. На конец — выполненное и один следующий шаг.
- По завершённой программе предлагать повторение и применение, а не циклически запускать первый урок.
- Нет наказания за пропуски, накопления бесконечного долга и скрытого изменения пользовательских сроков.

### Реализация

- Детерминированные правила поверх существующих статусов и ручной очереди. При наличии M4 использовать результаты вопросов; при наличии M5 — ближайший шаг проекта. Без них план всё равно полноценен.
- Оценки времени хранить как редакционные диапазоны; длительную практику делить на конкретный шаг. Не выводить неподтверждённую точность из количества слов.
- Хранить настройки, снимок плана, выполнение и паузу. План не перестраивается при каждом reload; обновление пользовательских статусов учитывается явно.
- Дата занятия определяется локальным календарным днём. Продумать полночь, смену часового пояса и параллельные вкладки.
- Выполнение пункта не должно автоматически означать освоение урока. Сохранить существующие ручные статусы и явное подтверждение результата.

### Приёмка

- Планы корректны для нового пользователя, частично пройденной программы, полностью пройденной программы и пустой очереди.
- План укладывается в заявленный приблизительный бюджет либо честно объясняет превышение/длинный шаг.
- Замена не возвращает тот же пункт без объяснения; пауза, reload и offline не теряют прогресс.
- Проверены смена дня и одновременное завершение пункта в двух вкладках.

**Проверка пользы:** время до начала полезного действия, доля завершённых занятий и оценка посильности плана. Только локальные агрегаты или добровольное исследование, без скрытой аналитики.

## M4. Повторение с проверкой понимания

**Результат:** очередь помогает обнаружить пробел и восстановить понимание, а не просто перечитать материал.

### Объём

- Первый выпуск: минимум 30 проверенных заданий в 3 ключевых модулях. Покрыть понятия, выбор действия и объяснение решения на кейсе.
- Цикл: вопрос → самостоятельный ответ → разбор → результат → следующий повтор. До отправки ответа объяснение скрыто.
- Закрытые задания имеют обоснованный ключ; открытые — рубрику и самооценку. Показывать различие этих результатов.
- При ошибке: объяснение, ссылка на конкретную тему и возможность повторной попытки. Не повторять тот же ответ немедленно как доказательство освоения.
- Автоматические интервалы доступны добровольно; ручная очередь и перенос сохраняются. Ограничивать дневную нагрузку, новые задания и повторяющиеся неуспехи.

### Реализация

- Реестр вопросов с ID, версией, навыком, ссылкой на материал, ключом/рубрикой и объяснением. Не публиковать вопросы без проверенных ответов.
- Отдельно хранить попытки, тип оценки и состояние расписания. Не переинтерпретировать старый статус «просмотрено» как правильный ответ.
- Зафиксировать простой алгоритм интервалов, границы, поведение после ошибки/пропуска и версию алгоритма. Сложный адаптивный алгоритм не нужен без проверенной необходимости.
- Сохранить историю при изменении вопроса; существенно обновлённый вопрос не наследует прежнюю оценку без явной политики.
- Статистика разделяет просмотр, самопроверку и объективно проверенные ответы. В M3 передавать приоритетные повторы через явный контракт.

### Приёмка

- 30 заданий проходят содержательную проверку; объяснения доступны и при правильном ответе.
- Тесты расписания используют управляемое время: успех, ошибка, пропуск, смена дня, лимит нагрузки и изменённый вопрос.
- Ответ и история переживают reload/backup/restore; двойная отправка не создаёт две попытки.
- Ручная очередь работает как раньше; пользователь может отключить автоматическое планирование.

**Проверка пользы:** успешность отсроченного ответа и решения нового похожего кейса. Не считать немедленное повторение вопроса достаточной проверкой понимания.

## M5. Рабочая тетрадь конкретного проекта

**Результат:** ответы из курса собираются в полезный документ для одной реальной или учебной задачи.

### Объём

- Несколько именованных проектов с явным активным проектом. Каждый содержит услугу, аудиторию, контекст, ограничения и цель.
- Сохранить все 10 этапов существующего итогового проекта, добавить общие данные, связи с практиками и обзор готовности.
- Прикреплять к этапу выбранную итерацию практики как снимок с указанием источника. Последующее изменение практики не меняет рабочий документ незаметно.
- Показать недостающие сведения и следующий шаг. Пользователь может работать в произвольном порядке; зависимости объясняются, а не блокируют работу.
- Итоговый просмотр и экспорт в Markdown/HTML для печати: контекст, этапы, выбранные ответы, допущения и нерешённые вопросы. JSON backup остаётся техническим переносом данных.

### Реализация

- Добавить сущности проекта и этапов с UUID и ревизиями. Переиспользовать редактор, историю и рубрики текущего `PracticeWorkspace.astro`.
- Существующие `FINAL_PROJECT` и старую общую заметку перенести в доступный проект «Мой первый проект» с восстановлением всех снимков. Не смешивать разные проекты по одному зарезервированному ID.
- При вставке практики показывать источник, дату и версию; обновление из новой итерации требует явного действия.
- Экспорт экранирует пользовательский текст; в документ не включаются скрытые технические поля и чужие проекты.
- Архивирование и восстановление проекта; окончательное удаление — отдельное явное действие. Личный поиск учитывает проект и не выдаёт его за материал курса.

### Приёмка

- Два проекта редактируются независимо; смена активного проекта не подменяет ответы и незаписанный черновик.
- Старые данные итогового проекта и копии v1/v2/v3 импортируются с сохранением заметки, этапов и истории.
- Снимок практики остаётся неизменным после редактирования оригинала; источник открывается по ссылке.
- Экспорт одного проекта читаем, печатается без обрезанных полей и не раскрывает другой проект; всё работает офлайн.

**Проверка пользы:** пользователь может собрать и применить итоговый оффер/предложение без ручного копирования ответов с десятка страниц.

## M6. Личная библиотека рабочих заготовок

**Результат:** пользователь создаёт и быстро находит собственные сообщения и документы для повторного использования.

### Объём

- В существующем справочнике: «Создать свой вариант». Личный каталог, создание с нуля, теги, поиск, избранное и архив.
- Первые категории: первое сообщение, discovery, предложение, возражение, follow-up. Подготовить минимум по одному проверенному стартовому шаблону на категорию.
- Переменные с подписями: услуга, клиент, контекст, следующий шаг. Предпросмотр готового текста и копирование без незаполненных маркеров.
- Несколько именованных версий, пояснение когда применять, заметка о фактическом результате. Результат пользовательский, без заявления доказанной конверсии.
- Связь с проектом M5 опциональна: подстановка только выбранных данных с предпросмотром; без M5 переменные заполняются вручную.

### Реализация

- Отделить публичный шаблон от личной копии. Обновление справочника не перезаписывает пользовательские изменения.
- Безопасный простой синтаксис переменных; не выполнять выражения или произвольный HTML. Не добавлять конструктор программирования.
- Хранить ID источника, версии текста, теги и контекст; неизменяемые версии позволяют восстановить предыдущий вариант.
- Копирование работает через Clipboard API с понятным fallback; функция ничего не отправляет клиенту автоматически.
- Частные шаблоны включаются в локальный поиск по явному выбору, backup и offline-сценарии.

### Приёмка

- Путь «выбрать исходник → создать копию → изменить → заполнить переменные → скопировать → восстановить версию» завершён.
- Проверены повторяющиеся/неизвестные переменные, пустые значения, длинный текст и отказ доступа к буферу.
- Исходник и чужие версии не меняются при работе с копией; архив не теряет данные.
- Поиск не отправляет личные тексты и не включает их в Pagefind.

**Проверка пользы:** время подготовки пригодного сообщения и доля заготовок, использованных повторно; избегать оценки качества только по числу копирований.

## M7. Выделения и заметки к конкретному месту

**Результат:** пользователь возвращается к собственному вопросу или выводу в точном контексте материала.

### Объём

- В учебном тексте выделить фрагмент и сохранить цитату с комментарием. Общие заметки к странице остаются.
- Личная панель выделений на странице и общий каталог с поиском, фильтром по модулю и переходом к источнику.
- Редактирование комментария, удаление с восстановлением и создание повтора из цитаты. Без M4 использовать существующую ручную очередь.
- На mobile предусмотреть touch-сценарий без перекрытия системного меню выделения; дать доступную альтернативу через выбор абзаца и ввод цитаты.

### Реализация

- Устойчивые ID блоков генерировать из канонического контента одинаково в Astro и fallback. Не привязываться только к порядковому номеру DOM-узла.
- Якорь хранит ID документа/блока, версию текста, точную цитату и контекст до/после. Смещения внутри блока — дополнительный, а не единственный ориентир.
- После обновления статьи искать точное однозначное совпадение. При неоднозначности помечать «место изменилось», сохранять цитату и предлагать ручную перепривязку. Не переносить комментарий на похожую фразу молча.
- Ограничить выделение основным учебным текстом; исключить элементы редакторов и навигацию. Проверить пересекающиеся выделения и работу с поисковой подсветкой.
- Представление выделений не изменяет исходный Markdown и не ломает ссылки, копирование, screen reader и выделение текста.

### Приёмка

- Сохранение, reload, переход из каталога и offline возвращают к правильному фрагменту.
- Тесты: несколько одинаковых цитат, изменённый/удалённый абзац, кириллица, пунктуация, несколько inline-элементов и пересечения.
- При потере привязки доступны исходная цитата и комментарий; ручное восстановление работает.
- Проверены клавиатура, touch на реальном или доступном эмулированном устройстве и отсутствие вмешательства в поля ответов.

**Проверка пользы:** пользователь находит сохранённый вывод и его контекст быстрее, чем через общую заметку; дополнительно отслеживать долю успешно восстановленных привязок при обновлениях контента.

## M8. Синхронизация телефона и компьютера

**Результат:** пользователь добровольно подключает аккаунт и продолжает работу на другом устройстве без потери локальных данных и конфликтующих версий.

### Объём и инфраструктурное решение

- Вход, подключение текущего локального пространства, статусы синхронизации, повтор ошибки, отключение устройства и выход.
- Синхронизировать прогресс, закладки, заметки, практики, историю, повторы и данные M1–M7. Настройки синхронизации и локальная установка offline-пакета не копируются как факт готовности другого устройства.
- До реализации оформить короткое архитектурное решение: провайдер auth, база, API, регион хранения, резервирование, стоимость, лимиты и восстановление аккаунта. Выбор подтвердить актуальной документацией и совместимостью с Vercel, без преждевременной миграции всего сайта на SSR.
- Нужны проект облачного сервиса, серверные секреты и согласованный бюджет. До предоставления инфраструктуры этап остаётся незавершённым; демонстрационный mock не считается готовой синхронизацией.
- Локальный режим доступен без регистрации. Перед первой загрузкой показать состав данных и явно запросить подключение; не отправлять автоматически найденные данные браузера.

### Протокол и сохранность

- Локальная запись немедленно сохраняется в user-store и ставится в durable outbox. Фоновая доставка идемпотентна: UUID операции, ревизия записи, подтверждение сервера, cursor получения изменений.
- Серверная ревизия и контроль конкуренции; время устройства не является единственным арбитром. Повтор после разрыва соединения не создаёт дублей.
- История попыток объединяется по ID; конкурирующие тексты сохраняются отдельными версиями с понятным сравнением. Статусы используют явную политику, позволяющую намеренный сброс. Не применять молча «последний timestamp побеждает» ко всем данным.
- Удаления передаются как tombstones с правилами срока хранения и возврата; проснувшееся старое устройство не воскрешает удалённую запись.
- Первое объединение облака и локальных данных имеет preview, локальную точку восстановления и подтверждение. Смена аккаунта не отправляет данные предыдущего: личные пространства изолированы по аккаунту, включая outbox и кеши частных ответов.
- Logout явно предлагает, сохранять ли данные данного аккаунта на устройстве. Следующий гость не должен неожиданно увидеть приватное пространство предыдущего пользователя.
- API требует авторизацию и проверку владельца каждой записи; серверная валидация размеров/форматов, лимиты запросов и защита auth-сессий. Секреты только на сервере.
- Частные API-ответы и auth-маршруты не кешируются общим service worker. Логи не содержат тексты ответов, токены и личные заметки.
- Предусмотреть экспорт, удаление облачных данных, срок хранения резервных копий и проверенное восстановление. Не обещать end-to-end encryption без отдельной реализации управления ключами.

### Интерфейс и эксплуатация

- Показывать «только на устройстве», «есть неотправленные изменения», «синхронизировано», «offline», «конфликт», «нужен вход» и время последней успешной доставки.
- Offline допускает работу и накопление операций. Истечение сессии не уничтожает локальные изменения; после повторного входа очередь продолжается безопасно.
- Разделить окружения разработки и production. Проверить резервирование, восстановление, мониторинг ошибок без содержимого данных и откат клиента/API при несовместимой версии.
- Для Python fallback: тот же клиентский протокол только при настроенном разрешённом API origin; иначе полноценная локальная работа и честная недоступность облака. Не открывать CORS для любых origins ради удобства.

### Приёмка

- Два независимых browser contexts/устройства: изменения доставляются в обе стороны; offline-изменения догоняют облако после подключения.
- Одновременная правка одной заметки сохраняет обе версии; удаление, reset статуса и повтор операции дают согласованный результат.
- Проверены первая загрузка больших данных, обрыв между записью и подтверждением, истечение сессии, неверные часы, превышение лимита, несколько вкладок и смена аккаунта.
- Пользователь A не читает и не изменяет данные B даже прямым API-запросом. Приватный кеш не раскрывает данные после выхода.
- Экспорт и восстановление всех восьми фич проверены; реальные backup/restore облака и удаление аккаунта испытаны в тестовом окружении.
- Production подключён к реальному сервису; smoke-проверка выполнена на тестовом аккаунте без затрагивания пользовательских данных.

**Проверка пользы:** успешность продолжения на втором устройстве, задержка доставки в контролируемом тесте, доля восстановимых ошибок и отсутствие потерь в конфликтных сценариях. Согласовать целевые значения после выбора инфраструктуры и измерения baseline.

## Общая приёмка каждого milestone

- Все обязательные пункты конкретного этапа реализованы; ограниченный контентный объём первого выпуска обозначен в интерфейсе и документации.
- Есть содержательно проверенные примеры/вопросы/сценарии, если они нужны фиче. Незаконченная редакционная проверка отмечена как блокер выпуска соответствующего контента.
- Основной поток и ошибки проверены в реальном браузере, обеих темах и соответствующих размерах. Итоговый дизайн-проход: иерархия, плотность, длинные тексты, focus и touch.
- Выполнены подходящие проверки из `npm run lint`, `npm run check`, `npm run build`, `npm run test:quality`, `npm run test:e2e`, `npm run test:fallback`; для offline-изменений дополнительно `npm run test:preview` на production preview. Зафиксированы реально выполненные команды и результаты, а не предполагаемый успех.
- Миграция старого состояния, round-trip нового backup, восстановление и межвкладочная работа проверены. Для M8 — дополнительно межустройственные сценарии и авторизация.
- Новый контент доступен в публичном поиске там, где это уместно; личный контент доступен только локально или через авторизованную синхронизацию. Offline manifest и обе сборки согласованы.
- Документация соответствует выпущенному поведению. Diff просмотрен, временные файлы удалены, commit отправлен в `origin/main`, deployment проверен.
- Нет оставленных mock-данных в production, неработающих кнопок и обязательных TODO внутри заявленного объёма. Отдельно записаны ограничения, которые пользователь действительно увидит.

## Оценка результата и дальнейшее расширение

Перед каждым этапом зафиксировать baseline и 2–3 проверяемые гипотезы на небольшом добровольном пользовательском тесте. По итогам сравнить удобство и качество результата, затем решать о расширении объёма. Время в приложении, число кликов и серии посещений сами по себе не доказывают пользу.

Контентные границы M1 (10 практик), M2 (6 сценариев) и M4 (30 заданий / 3 модуля) — явный объём первого законченного выпуска, а не обещание покрытия всех 336 уроков и 72 практик. Расширение корпуса — отдельная редакционная работа после проверки первых выпусков.

Исследовательская основа предложений: [обзор retrieval practice](https://eric.ed.gov/?id=EJ1319572), [RemNote: планирование подготовки](https://help.remnote.com/en/articles/9101991-preparing-for-an-exam), [Readwise: возвращение к выделениям](https://docs.readwise.io/readwise/docs/faqs/reviewing-highlights), [Duolingo: Roleplay](https://blog.duolingo.com/duolingo-max/), [Coursera: сценарная практика](https://blog.coursera.org/new-ai-powered-innovations-on-coursera/). Это источники принципов и примеров, а не доказательство будущих результатов Sales OS.
