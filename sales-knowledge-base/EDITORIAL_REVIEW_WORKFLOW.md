# Рабочий процесс редакторской проверки

Файл `editorial-review-ledger.json` хранит актуальные записи проверки тезисов. Он не подтверждает материал автоматически: производные индексы, тесты и сборка не могут менять `editorial_draft` на `verified`.

## Запись проверки

Каждая запись относится к одному документу, тезису и решению рецензента:

| Поле | Требование |
|---|---|
| `recordId` | Уникальный стабильный ID записи. |
| `documentId` | ID документа из front matter: модуль, урок или практика. |
| `claimId` | Устойчивый ID конкретного тезиса внутри документа; не переиспользовать для другого тезиса. |
| `claim` | Проверяемая формулировка тезиса или предмет проверки. Не обозначать весь материал общим словом «верно». |
| `sourceIds` | Один или несколько ID источников из каталога и списка `sources` этого документа. Источник должен подтверждать именно отмеченный тезис. |
| `checkedOn` | Дата последней проверки в формате `YYYY-MM-DD`. |
| `scope` | Что именно проверено: издание и глава/страница, юрисдикция, канал, редакция правила платформы или иной ограничивающий контекст. |
| `reviewer`, `reviewerRole` | Ответственный человек и его релевантная роль/квалификация. Автоматический тест или языковая модель не являются рецензентом. |
| `coverage` | `selected_claims` — только указанный тезис; `full_document` — весь документ, включая примеры, расчёты, источники и практическую задачу. |
| `reviewType` | `editorial`, `legal` или `platform`. Право и правила каналов проверяются профильным специалистом. |
| `status` | `verified` — проверка пройдена в указанном scope; `needs_revision` — найдена проблема или материала для вывода недостаточно. |
| `specialistConfirmed` | Для `verified` записей типов `legal` и `platform` обязательно `true`, подтверждённое профильным рецензентом. |

## Порядок работы

1. Открой исходный Markdown и сформулируй проверяемый тезис с устойчивым `claimId`. Не переноси общую ссылку на весь документ как доказательство каждой его мысли.
2. Изучи первоисточник в указанной версии. Для права и быстро меняющихся правил явно зафиксируй юрисдикцию/канал и дату; одна только страница источника в каталоге недостаточна.
3. Заполни scope и источник, который непосредственно подтверждает тезис. Если проверка не покрывает весь материал, укажи `selected_claims`.
4. Укажи человека-рецензента, роль, дату и `verified` либо `needs_revision`. При юридической или платформенной проверке поставь `specialistConfirmed: true` только после подтверждения специалистом.
5. Если требуется исправление, оставь front matter документа `editorial_draft`, внеси правки и повторно проверь тезис. Запись отражает актуальное решение; при повторной проверке обнови ту же запись и дату. Git-история сохраняет историю изменений исходника.
6. Для перехода документа в `verified` должны быть завершены **все** его записи, среди них должна быть минимум одна запись `full_document`, и каждая запись должна быть `verified`. Только затем меняй статус front matter. Частичная выборочная проверка сама по себе не делает документ проверенным.
7. Запусти `npm run prepare:content`. Валидатор проверит ID документов и источников, дату, полноту полей, профильную отметку для права/платформ и соответствие статуса документированным записям. Затем проверь страницу `/editorial-review/`.

## Текущий gate

Пустой реестр означает, что независимые проверки не зарегистрированы. На дату roadmap все 430 основных документов остаются `editorial_draft`; связанные источники обозначают направления для изучения, а не подтверждение тезисов. Техническая приёмка приложения не закрывает редакторский gate M5-CONTENT.
